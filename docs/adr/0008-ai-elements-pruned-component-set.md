# AI Elements for the chat UI, pruned to a minimal component set

## Context

The hand-rolled chat UI from initial scaffolding ([ADR-0001](./0001-nextjs-fullstack-single-app.md), built directly on shadcn/ui primitives — `Card`, `Avatar`, `Badge`, `Input`, `ScrollArea`) worked functionally but looked unstyled in the browser. Root cause (unrelated to this ADR, fixed separately): `app/globals.css` had `@import "shadcn/tailwind.css"`, a path that doesn't exist in the installed `shadcn` package (which is only the CLI, not an importable stylesheet) — silently breaking Tailwind's build. While fixing the visual bug, the user asked to adopt [AI Elements](https://ai-sdk.dev/elements) — a component registry built on shadcn/ui specifically for `useChat`-driven interfaces — and noted a matching skill was already available locally at `.agents/skills/ai-elements`.

Running `pnpm dlx ai-elements@latest` with no arguments installs its **entire catalog by default**: ~50 components spanning far more than a chat UI needs (agent-builder canvases, terminals, sandboxes, voice/speech input, file trees, web previews), plus every shadcn/ui primitive any of those touch (`carousel`, `dialog`, `tabs`, `command`, `popover`, `switch`, …). Left as installed, this would have added ~40 files and ~9 npm packages (`@xyflow/react`, `@rive-app/react-webgl2`, `media-chrome`, `embla-carousel-react`, `ansi-to-react`, `motion`, `react-jsx-parser`, `tokenlens`, `@radix-ui/react-use-controllable-state`) with zero relevance to a text-based automotive sales/service assistant — exactly the kind of accumulated bloat the user's "check what's needed and what's redundant" instruction was aimed at.

Separately, one of the components this project *does* need — `prompt-input.tsx` — failed `pnpm build`'s type check against the installed `@base-ui/react@1.8.0` (the underlying primitive library shadcn/ui's `Button`, `HoverCard`, and `DropdownMenu` are now built on). Confirmed as a genuine upstream version-skew bug in the ai-elements registry itself, not a local misconfiguration, by reproducing the same failure directly against Base UI's current release outside this project.

## Decision

Installed the full AI Elements catalog (required — the CLI has no selective-install mode when run non-interactively), then computed the actual transitive dependency closure of only the components `app/page.tsx` imports (`conversation`, `message`, `prompt-input`, `tool`, `suggestion`, plus `code-block` as `tool`'s JSON-display dependency), and deleted everything outside that closure: 41 `ai-elements` components, 10 `ui` primitives (9 immediately + `hover-card` once its only caller inside `prompt-input.tsx` was removed), and the 9 orphaned npm packages listed above.

Within `prompt-input.tsx` itself, went further than file-level keep/delete: removed its unused attachment-upload and screenshot menu items, and its `PromptInputHoverCard`/`Trigger`/`Content` wrapper — the exact pieces that failed the Base UI type check, and which this project doesn't use. `PromptInputSubmit`, which *is* used, had a narrower version of the same bug (its internal click handler's event parameter was typed as plain `React.MouseEvent` while Base UI's `Button` now wraps events in a `BaseUIEvent<T>` type) — fixed in place by deriving the handler's parameter type from the `onClick` prop itself (`Parameters<NonNullable<typeof onClick>>[0]`) rather than hardcoding a type, so it tracks whatever Base UI expects instead of drifting out of sync again.

`components/ai-elements/` and `components/ui/` are excluded from Biome's lint scope entirely (established in [ADR-0007](./0007-biome-ultracite-over-eslint.md)) — they're vendored registry code, and the pruning above is the extent of hand-editing intended for them.

## Considered options

1. **Install everything, delete the unused majority down to a computed dependency closure (chosen).** The CLI offers no non-interactive selective install, so this was the only way to reach a minimal footprint without hand-guessing which files import which — the closure was computed programmatically (walk `@/components/...` and relative imports from the 5 seed files) rather than eyeballed, specifically to avoid missing a transitive dependency and shipping a broken import.
2. **Keep the full install.** Zero pruning effort, but ships ~40 irrelevant files and several heavy, unused npm packages (a graph-visualization library, a WebGL animation runtime, a terminal ANSI renderer) into a project whose entire UI surface is a text chat window — directly contrary to what was asked.
3. **Hand-write a custom chat UI instead of adopting AI Elements.** What was already in place before this session (see Context) — rejected because the user explicitly asked to switch to AI Elements, and because `Tool`'s collapsible, state-aware display is a meaningfully better fit for showing tool calls than the Badge-based approach it replaced.
4. **Wait for the ai-elements registry to fix the Base UI type mismatch upstream, rather than patching locally.** Rejected as the primary path: blocks `pnpm build` today with no ETA, for a fix that's small, well-understood, and confined to code paths this project doesn't use. The patch is documented inline in `prompt-input.tsx` and here, and a straightforward `pnpm dlx ai-elements@latest add prompt-input --overwrite` re-fetches the current registry version if/when it's fixed upstream and attachment/hover-card support is ever wanted.

## Consequences

- Final UI footprint: 6 `ai-elements` files + 15 `ui` primitives, down from ~50 + ~24 as installed — see `docs/PRD.md` §3a for the exact kept/removed lists.
- `Tool` (from `ai-elements`) replaces the earlier hand-rolled `Badge`-based tool-call indicator with a collapsible, state-aware display (pending/running/completed/error), directly serving the BRD rubric's "graceful error handling" and general UX criteria.
- `MessageResponse` renders assistant text through `streamdown` (GFM markdown, math, code blocks with syntax highlighting via `shiki`) instead of the earlier plain-text `Card`, which is a real capability gain for anything the model formats as markdown (e.g. a bulleted list of vehicle specs).
- **Reinstalling or updating any trimmed AI Elements component later requires re-checking it against whatever `@base-ui/react` version is current at the time** — the version-skew bug that forced this session's `prompt-input.tsx` edits could recur or could already be fixed upstream; `pnpm dlx ai-elements@latest add <component> --overwrite` followed by `pnpm build` is the way to find out.
- The dependency-closure computation (a small Python script walking import statements) isn't saved anywhere in the repo — if the AI Elements component set needs re-pruning after a future update, that closure logic needs to be redone rather than rerun.

## Update: a second, unrelated styling bug in the same file

After the fix above, the UI still didn't look right — fonts and spacing were off in a way that wasn't the missing-import bug. Root cause: `app/globals.css`'s `@theme inline` block had `--font-sans: var(--font-sans);` — a **self-referential** custom property. CSS resolves a circular `var()` reference to nothing valid, so `html { @apply font-sans; }` silently fell back to the browser's default font stack instead of the Geist Sans font actually loaded in `app/layout.tsx` (which sets the *differently-named* variable `--font-geist-sans`). Confirmed by grepping for the self-reference pattern (only this one instance existed) and by checking the compiled CSS and rendered `<html>` element before and after: the Geist font module classes were present on `<html>` the whole time, they just weren't wired to anything `font-sans` resolved to. Fixed by pointing `--font-sans` at `var(--font-geist-sans)` instead of itself.

Not a Biome/Ultracite issue — that toolchain lints and formats JS/TS, not CSS custom-property values, and this line was untouched by any lint autofix in this session's history. Both this bug and the `shadcn/tailwind.css` import bug above trace to the same file (`app/globals.css`) and the same root cause: it came out of the initial `shadcn init` scaffold with content that doesn't match this project's actual font-loading setup, and nothing in the build pipeline catches an invalid CSS custom property at compile time the way TypeScript would catch a bad import.

## Update: visual redesign for a denser, "chunkier" chat feel

Once the two styling bugs above were fixed, the UI rendered correctly but still looked plain compared to consumer chat products (ChatGPT, Claude) — the user asked for bigger text, more breathing room, and a more substantial ("chunky") feel throughout. This was a styling pass, not an architecture change, but the *mechanism* used to make it — and one dead end hit along the way — is worth recording, since the same constraint will recur for any future styling work on these components.

**What changed**: larger body text (`text-sm` → `text-base`) and relaxed line-height on message content; user-message bubbles went from a flat `rounded-lg` box to a `rounded-3xl` pill with more padding (assistant messages stay bubble-less by AI Elements' own convention — only the user side is a "bubble," matching ChatGPT/Claude); a branded icon badge added to the header; bigger pill-shaped suggestion buttons; more vertical spacing between sections; and the prompt input's textarea got bigger padding and a guaranteed `text-base` (it was silently shrinking to `text-sm` at the `md:` breakpoint via Tailwind's default `Textarea` styles — visible only on desktop, easy to miss).

**The dead end**: `PromptInput`'s rounded/bordered input "shell" (`InputGroup`) isn't exposed as a `className`-able prop — it's hardcoded two levels down inside `prompt-input.tsx`. The first attempt avoided editing vendored code by targeting it from `app/page.tsx` with a Tailwind arbitrary descendant selector keyed off its `data-slot="input-group"` attribute: `[&_[data-slot=input-group]]:rounded-2xl`. This **silently failed** — no error, no warning, the utility just never appeared in the compiled CSS. Confirmed by fetching the actual compiled stylesheet and grepping for the target rule directly, twice (first with an over-strict grep pattern that produced a false negative, then again with a looser one that confirmed the truth: the nested-bracket arbitrary variant genuinely never compiled). Tailwind v4's arbitrary-variant parser apparently doesn't reliably handle a `[data-slot=...]` attribute selector nested inside an `&_[...]` descendant-combinator variant, at least not in this setup — worth knowing before reaching for that pattern again.

**The fix**: abandoned the selector approach and edited `prompt-input.tsx`'s `InputGroup` element directly, adding the chunky classes (`rounded-2xl border-2 shadow-sm`, plus a focus-state shadow) right where it's rendered. This is the same file already hand-edited for the Base UI typing bug above, and the same customization path AI Elements' own docs endorse ("style or configure the component just as you would if you wrote it yourself"). Verified by fetching the compiled CSS again and confirming the actual `border-radius`/`border-width`/`box-shadow` rules exist this time, not just the class names sitting inert in the HTML.

**Takeaway for future styling work on this component set**: where a component exposes `className` directly on the element you need (`Message`, `MessageContent`, `ConversationContent`, `Suggestion`'s `size` prop, `PromptInputTextarea`), override from `app/page.tsx` — including `group-[.is-user]:` variant-prefixed overrides for `MessageContent`'s user-bubble styling, which `cn()`'s tailwind-merge resolves correctly against the component's own same-prefixed defaults. Where the element you need to reach isn't exposed as a prop (like `InputGroup` here), edit the vendored file directly rather than reaching for a `data-slot`-keyed arbitrary selector — the latter looks like it should work and doesn't reliably.
